## 第 1 章 总体设计

### 1.1 部署形态

```
┌─────────────────────────────────────────────────────────┐
│ 浏览器（手机优先，兼容桌面）                                │
│                                                         │
│  gate.html   index.html   story.html   write.html  me.html │
│      │           │            │           │          │   │
│      └───────────┴────────────┴───────────┴──────────┘   │
│                          │                              │
│                   assets/api.js  ← 唯一取数出口            │
│                          │                              │
│         localStorage: session_token / device_id         │
│         sessionStorage: gate_ok / request_id / 草稿       │
└──────────────────────────┬──────────────────────────────┘
                           │ https
                           │ POST /.cloud/database/rest/rpc/api_xxx
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 托管平台                                                  │
│   静态资源（html/css/js/jpg）                              │
│   数据面 PostgREST  ←─ 只转发到 public schema 的函数        │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 托管 PostgreSQL                                          │
│   ├── 14 个 api_* 函数（SECURITY DEFINER，业务全在这里）    │
│   ├── 6 张表（对 anon / authenticated 零授权）              │
│   └── 约束、部分索引、唯一索引                             │
└─────────────────────────────────────────────────────────┘
```

**三条不能破的边界**

1. 前端只调 `api_*`，**不读表、不写表**。表对前端没有授权，绕过只有 42501。
2. 函数是唯一能做判断的地方：身份、权限、状态、计数、排序。
3. 表只负责它擅长的：唯一、外键、CHECK、索引。

### 1.2 模块职责

| 层 | 模块 | 职责 | 明确不负责 | 依赖 |
|---|---|---|---|---|
| 前端 | 页面层（5 个 html） | 结构、交互、页面状态机、表单体验校验 | 权限判定、最终校验、计数、排序 | api 层、视觉层 |
| 前端 | `assets/api.js` | 协议封装、凭证存取、错误归一（code → 异常） | 任何业务规则 | 平台 SDK |
| 前端 | `assets/style.css` | 设计令牌、组件样式、响应式 | 逻辑 | 无 |
| 前端 | 本地存储 | token / device / gate_ok / request_id / 草稿 | 业务数据 | 无 |
| 服务端 | 函数层（14 个 `api_*`） | 鉴权、参数校验、事务、幂等、统计、限流 | 排版、文案拼装、HTML | 数据层 |
| 服务端 | 数据层（6 表） | 唯一、外键、CHECK、索引 | 业务提示文案 | 无 |

**为什么前端不能自己判「这条是不是我的」**：JavaScript 里判出来的结果只影响显示，不影响服务端放行，等于没判。所有判权必须落在函数里。

### 1.3 模块交互关系

```
页面层 ──①调用──▶ api.js ──②rpc──▶ api_* 函数 ──③SQL──▶ 表
  ▲                  │                  │
  │                  │                  └─④返回封套 {code,message,data}
  └──⑤data 或 throw──┘
```

| 编号 | 协议 | 约束 |
|---|---|---|
| ① | 页面调 `api.xxx(params)` | 页面不得自行发请求，不得读 localStorage 里的 token |
| ② | `cloud.database.rpc(函数名, 参数对象)` | 形参一律 `p_` 前缀；只传 JSON 可序列化值 |
| ③ | 函数内 SQL | 只访问 `public` schema；判权用 `author_id` |
| ④ | 统一封套 | 成功 `code=0`；失败 `code≠0` + 中文 `message` |
| ⑤ | `api.js` 出口 | `code≠0` 一律 throw `ApiError`，**不返回可疑数据** |

**依赖方向是单向的**：页面 → api → 函数 → 表。反向依赖（函数调前端、表里存 JSON 逻辑）一律禁止。

### 1.4 为什么没有传统后端

平台不提供 Node / Edge Function，服务端逻辑只能写成 PostgreSQL 函数。这条约束带来三好三坏，接手前应当知道：

| 好 | 坏 |
|---|---|
| 事务天然：发布「写 story + 写 tag」、认领「换设备 + 换码 + 换 token」都在一个函数体内，失败整体回滚，不需要前端补偿 | 业务逻辑用 SQL 写，调试和 review 都比 JS 难，接手门槛高 |
| 少一层部署，没有服务器要运维，也没有进程要重启 | 错误不能改 HTTP 状态码，只能走响应体 `code`（2.4） |
| 权限写在同一处（函数 + 表授权），不存在「某个接口忘了加校验」的漏网 | 不能下发 Cookie、不能设缓存头、不能做长连接 |

## 第 2 章 通信协议

本章是前后端联调的唯一依据。**凡本章未定义的返回，视为未定义行为。**

### 2.1 传输方式：RPC，不是 REST

所有调用都是对 PostgreSQL 函数的远程调用（PostgREST 的 `/rpc` 端点）：

| 项 | 约定 |
|---|---|
| 方法 | 统一 POST（读接口也是 POST） |
| 路径 | `/.cloud/database/rest/rpc/{函数名}`，由 SDK 拼装，前端不手写 |
| 参数 | JSON 对象，键名 = 函数形参名 |
| 前端唯一入口 | `cloud.database.rpc('api_story_list', {...})` |

**禁止事项**（做了会绕过鉴权或直接报错）：

- 手写 `fetch` 打 `/.cloud/**`
- `cloud.database.from('story').select()` 直接查表
- 把参数拼进 URL 或 header
- 自己解析 `p_token`

### 2.2 调用形态

```js
// 读
const { data, error } = await cloud.database.rpc('api_story_list', {
  p_token:   session.token,
  p_topic:   'study',
  p_status:  null,
  p_keyword: null,
  p_page:    1,
  p_size:    10,
});

// 写
const { data, error } = await cloud.database.rpc('api_story_create', {
  p_token:      session.token,
  p_payload:    { title, body_before, topic_code, life_stage, nickname },
  p_request_id: session.requestId,
});
```

**命名约定**

| 约定 | 理由 |
|---|---|
| 形参一律 `p_` 前缀 | 函数体内列名优先于形参，`p_` 能避免 `status` 这类同名歧义 |
| 可选参数传 `null`，不传 `undefined` | JSON 序列化会丢掉 `undefined` 键，函数侧看到的参数个数会变 |
| 复合输入用 `p_payload jsonb` | 一次传对象，避免形参列爆炸；校验在函数内逐字段做 |

### 2.3 统一封套

```json
{ "code": 0, "message": "", "data": { } }
```

| 字段 | 类型 | 必返 | 说明 |
|---|---|---|---|
| `code` | integer | 是 | 0 = 成功；非 0 见附录 A |
| `message` | string | 是 | **可直接展示给用户的中文**；`code=0` 时为空串 |
| `data` | object \| null | 是 | 成功时的载荷；失败时为 `null`（个别错误会带补充信息） |

硬规则：

- 所有 `api_*` 返回类型固定为 `jsonb`
- 函数**不得让异常逃逸**到 PostgREST（除极端情况），一律 `RETURN` 封套
- `data` 里不出现数据库列名（不返回 `owner_id`、`author_id`），只出现业务字段名
- `message` 不包含 SQL 错误原文、表名、字段名、堆栈

### 2.4 错误表达与前端唯一出口

**HTTP 状态码恒为 200。** 原因：PostgREST 只在函数抛未捕获异常时返回 400/500，那是平台格式，前端控制不了；既然控制不了，就不要让前端依赖它。

因此前端必须在唯一出口把 `code` 转成异常：

```js
// assets/api.js
async function call(fn, params) {
  if (!client) throw new ApiError('NO_CLOUD', '云服务还没开通，页面只能看版式');
  const { data, error } = await client.database.rpc(fn, params);
  if (error)                       throw new ApiError('RPC_ERROR', '服务异常，稍后再试', error);
  if (!data || typeof data.code !== 'number')
                                   throw new ApiError('BAD_SHAPE', '服务返回格式不对');
  if (data.code !== 0)             throw new ApiError(data.code, data.message, data.data);
  return data.data;                 // 页面只拿到 data，永远拿不到 code
}
```

**为什么把 `code` 挡在 api.js 里**：页面拿不到 `code`，就不可能写出「忘了判断」的代码。

**已知副作用**：浏览器 Network 面板里所有请求都显示 200，联调时容易把失败当成功。排查手段是看响应体的 `code`，或临时在 `call()` 里打印。

### 2.5 数据类型约定

| 类型 | 约定 |
|---|---|
| 时间 | 库里 `TIMESTAMPTZ` 存 UTC；接口一律返回 ISO 8601 带 `Z`，如 `2026-10-27T13:05:00Z`。前端 +8 小时展示；「3 天前」这类相对时间由前端算，服务端不返回 |
| 标识 | `story_id`、`user_id` 为整数；前端当不透明值，不做运算、不拼字符串比较 |
| 空值 | 无值一律 `null`，不用空字符串顶替；字符串字段返回时保证是字符串或 `null`，不会缺键 |
| 布尔 | `true` / `false`，不用 0/1（数据库里 `SMALLINT` 的 0/1 在函数里转成布尔再返回） |
| 字符串长度 | 一律按 Unicode 码点计（`char_length`）。**前端 JS 的 `length` 对 emoji 计数不同，故以服务端校验为准**，前端长度提示只是体验 |
| 数字 | `thanks_count`、`total` 为非负整数 |
| 数组 | `tags` 永远是数组，可能是空数组 `[]`，不会是 `null` |

### 2.6 分页协议

**请求**

| 参数 | 类型 | 默认 | 约束 |
|---|---|---|---|
| `p_page` | integer | 1 | 1 起；超过 10 按 10 处理并置 `truncated` |
| `p_size` | integer | 10 | 1–10；超过 10 按 10 处理 |

**响应 `data`**

```json
{
  "items": [],
  "total": 24,
  "page": 1,
  "size": 10,
  "has_more": true,
  "truncated": false
}
```

| 字段 | 说明 |
|---|---|
| `total` | 符合当前筛选的总条数，**已排除示例内容**（3.10） |
| `has_more` | `page × size` 小于 `total` |
| `truncated` | 请求页码超过上限时为 true，前端提示「显示前 100 条，可用搜索缩小范围」 |

**排序**：`created_at DESC, story_id DESC`。第二排序键必须有，否则同秒创建的两条在不同页请求里顺序可能翻转，出现「翻页丢数据」。

**为什么不用 cursor**：总量上限 100 条，offset 足够；cursor 会引入「游标失效」这类新问题，收益为零。

### 2.7 幂等协议

只对**发布**（`api_story_create`）实现。

| 项 | 约定 |
|---|---|
| 键 | `p_request_id`，UUID v4 字符串（36 字符，含连字符） |
| 生成时机 | 打开投稿表单时生成一次，存 `sessionStorage` |
| 作用域 | 全库唯一（`story.request_id` 唯一索引） |
| 命中行为 | 返回**已有那条记录**的 `story_id`，`data.duplicated = true`，不新建 |
| 清理时机 | 提交成功后前端清掉；用户放弃表单时保留（重开同一表单仍用同一个键） |

**语义**：重复提交不是错误。前端拿到 `duplicated: true` 时提示「这次提交已经成功过了」，而不是弹红字。

**其他写接口不做幂等**，理由：编辑、删除、补写、致谢在「同参数重复执行」下结果一致，天然幂等；而致谢本身由唯一索引兜底（重复致谢计数不变）。

### 2.8 鉴权协议

三段式，口令只在前两步出现：

```
① 口令 ──api_gate_verify──▶ gate_ok（短期标记）
② gate_ok ──api_session_init──▶ session_token（长期凭证）
③ session_token ──其余 12 个接口──▶ 身份
```

| 凭证 | 存放 | 有效期 | 何时失效 |
|---|---|---|---|
| `gate_ok` | `sessionStorage` | 关标签页即失效 | 换到 token 后不再需要 |
| `session_token` | `localStorage` | 长期 | 认领迁移、主动重置恢复码、用户清缓存 |

**传递方式**：作为 `p_token` 参数，**不放 header**。平台不放行自定义请求头，这条路走不通。

**函数侧统一前置校验**（每个 `api_*` 开头都必须有）：

```sql
SELECT user_id INTO v_uid FROM app_user WHERE session_token = p_token;
IF v_uid IS NULL THEN
  RETURN jsonb_build_object('code', 40101, 'message', '身份已失效，请重新打开页面');
END IF;
```

**故意不区分**「没传 token」与「token 错误」，都返回 40101，避免攻击者用错误码差异探测 token 是否存在。

**口令只校验一次**：`api_gate_verify` 通过后，后续请求不再校验口令。这样口令不会在每次请求里重复出现在网络上，也避免「改了口令要重新输」的体验断层。

### 2.9 限流协议

计数落表 `rate_limit`，函数内自增；窗口固定，不做滑动窗口。

| bucket | subject | 窗口 | 上限 | 超出返回 |
|---|---|---|---|---|
| `gate_fail` | ip | 10 分钟 | 10 次 | 42903（并锁 30 分钟） |
| `claim_fail` | ip | 10 分钟 | 5 次 | 42902（并锁 30 分钟） |
| `publish` | `device_id` | 10 分钟 | 3 条 | 42901 |
| `new_identity` | ip | 24 小时 | 20 个 | 42906 |

**诚实说明（必须写在这里，不能只写在评审意见里）**：`ip` 由前端上报，**可以伪造**。所以这四条限流只防手滑和低成本的重复点击，防不住有意刷。真正的底线是 `story.request_id`、`thanks` 主键、`app_user.device_id` 三个唯一约束。对外不要说成「防刷机制」。

### 2.10 兼容与演进

| 规则 | 说明 |
|---|---|
| 函数只加参数，不改语义 | 新增参数必须有默认值，否则旧调用直接报错 |
| 响应只加字段 | 不删字段、不改类型、不改含义 |
| 前端必须忽略不认识的字段 | 不允许「遇到未知字段就报错」 |
| 破坏性变更用新函数名 | `api_xxx_v2`，旧函数保留一个版本周期后再删 |
| 枚举只增不减 | `topic_code` 加新值可以，改已有值的含义不行 |

### 2.11 协议层已知弱点

写在这里，而不是留到答辩时被问：

| # | 弱点 | 影响 | 缓解 |
|---|---|---|---|
| P-1 | token 存在 localStorage，XSS 可窃取 | 身份被冒充 | 用户内容一律 `textContent`；不引第三方脚本；认领/重置换发 token（5.5） |
| P-2 | 错误走 200 | 监控里「全是成功」，日志失真 | 前端唯一出口转异常；联调看响应体 `code` |
| P-3 | 限流 IP 不可信 | 限流可绕过 | 靠唯一约束兜底，不宣称防刷 |
| P-4 | 不能设缓存头 | 每次列表都打到数据库 | 数据量小（百条级），可接受 |
| P-5 | 函数无超时控制 | 慢查询占连接 | 索引已覆盖查询；上线前用 500 条压测（8.2） |

## 第 3 章 数据结构

### 3.1 表与关系

```
app_user ──1:N── story ──1:N── story_tag
                    │
                    └──1:N── thanks（联合主键防重）

app_config   独立（3 行配置）
rate_limit   独立（计数，可清）
```

V1 只有 6 张表。`report`（举报）与 `admin_log`（后台）属 V1.1，**现在不建**——空表不是提前准备，是多维护一份没人用的结构。

### 3.2 `app_user` — 身份

一台设备一行。迁移时**只更新这一行**。

| 字段 | 类型 | 可空 | 默认 | 说明 |
|---|---|---|---|---|
| `user_id` | BIGSERIAL | 否 | 自增 | 主键。**story 判权的依据** |
| `device_id` | VARCHAR(40) | 否 | — | 设备标识，唯一。清缓存可再生 |
| `session_token` | CHAR(64) | 否 | — | 会话凭证，64 位小写十六进制。唯一 |
| `nickname` | VARCHAR(40) | 否 | — | 昵称，2–12 字，唯一。作者自填（R6-6） |
| `recovery_code` | CHAR(12) | 否 | — | 恢复码，12 位大写字母+数字（剔除易混字符） |
| `nickname_changed` | SMALLINT | 否 | 0 | 0 未改过 / 1 已改过（只能改一次） |
| `created_at` | TIMESTAMPTZ | 否 | now() | |
| `last_seen_at` | TIMESTAMPTZ | 否 | now() | 每次 init / 认领时更新 |

**约束**

| 名称 | 内容 | 为什么 |
|---|---|---|
| `uk_user_device` | UNIQUE(device_id) | 一设备一身份；认领时靠它发现冲突 |
| `uk_user_token` | UNIQUE(session_token) | 凭证不能撞 |
| `uk_user_nickname` | UNIQUE(nickname) | R6-7 要求全库唯一，冲突时提示换名 |
| `uk_user_code` | UNIQUE(recovery_code) | 码要能唯一定位一个人 |
| `ck_user_code_len` / `ck_user_code_set` | 长度 12，字符集 `[23456789A-HJ-NP-Z]` | 剔除 0/O/1/I 等易混字符，抄写不出错 |
| `ck_user_nick_len` | 2 ≤ len ≤ 12 | R6-6 |
| `ck_user_token_len` | 匹配 `^[0-9a-f]{64}$` | 防止代码里传了短串还以为成功 |

**写入时机**

| 时机 | 动作 |
|---|---|
| 首次 `api_session_init` | 插入一行（生成 token / 恢复码 / 默认昵称） |
| 每次 `api_session_init` 命中已有设备 | 更新 `last_seen_at` |
| `api_claim` 成功 | 更新 `device_id`、`session_token`、`recovery_code`、`last_seen_at`；**story 一行不动** |
| `api_recovery_reset` | 更新 `recovery_code`（旧码立即失效） |

### 3.9 统计口径（最容易被算错的一条）

主题条数与「共 N 条」**一律排除示例内容**：

```sql

  FROM story
 WHERE status IN ('open','resolved')
   AND deleted_at IS NULL
   AND source_type = 'user'        -- 少了这一行，示例内容会被算进条数
 GROUP BY topic_code;
```

对应验收 AC-11：构造 3 条真实 + 6 条示例，页面必须显示 3 而不是 9。

### A-01 `api_gate_verify` — 口令校验

**用途**：验证前台访问口令。通过后发一个短期标记 `gate_ok`，用于换正式 token。

**签名**

```sql
api_gate_verify(p_pass text, p_ip text DEFAULT NULL) RETURNS jsonb
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `p_pass` | text | 是 | 用户输入的口令原文 |
| `p_ip` | text | 否 | 前端上报的 IP，仅用于失败计数。**不可信**（2.9） |

**返回 `data`**

```json
{ "gate_ok": "9f2c…", "expires_in": 3600 }
```

| 字段 | 说明 |
|---|---|
| `gate_ok` | 64 位十六进制串的 SHA-256 摘要值（取前 32 位），有效期 1 小时 |
| `expires_in` | 距离失效的秒数，前端不用它做判断，只用于调试 |

**错误码**

| 码 | 触发 |
|---|---|
| 40301 | 口令错误 |
| 42903 | 同一 IP 10 分钟内失败 10 次，锁定 30 分钟 |
| 50001 | 口令哈希缺失（配置未初始化） |

**实现要点**

`gate_ok` 不落库、不用密钥，用口令哈希 + 时间片自己算：

```sql
SELECT value INTO v_hash FROM app_config WHERE key = 'gate_pass_hash';

-- 1. 锁定检查
SELECT value INTO v_lock FROM app_config WHERE key = 'gate_locked_until';
IF v_lock IS NOT NULL AND v_lock::timestamptz > now() THEN
  RETURN jsonb_build_object('code', 42903, 'message', '试得有点多，稍后再试');
END IF;

-- 2. 口令比对（pgcrypto）
IF crypt(p_pass, v_hash) <> v_hash THEN
  -- 失败计数 +1；达到 10 次则写 gate_locked_until = now() + 30min
  RETURN jsonb_build_object('code', 40301, 'message', '口令不正确');
END IF;

-- 3. 签发小时级标记
v_ok := left(encode(digest(v_hash || to_char(date_trunc('hour', now()), 'YYYYMMDDHH24'), 'sha256'), 'hex'), 32);
RETURN jsonb_build_object('code', 0, 'message', '',
  'data', jsonb_build_object('gate_ok', v_ok, 'expires_in', 3600));
```

**为什么这么算**：平台不给环境变量，也就没有签名密钥可用。用「口令哈希 + 当前小时」做输入，等价于一个只在 1 小时内有效的凭据，且口令一改，旧标记自然全废。不落库意味着不需要清理，也不会成为并发瓶颈。

**注意**：`session_init` 校验时必须接受**当前小时和上一小时**两个值，否则整点前后会有一批用户被踢回门页。

### A-02 `api_session_init` — 建号 / 取会话

**用途**：用 `gate_ok` 换正式 `session_token`。首次调用建号，之后每次刷新 `last_seen_at`。

**签名**

```sql
api_session_init(p_device text, p_gate_ok text, p_ip text DEFAULT NULL) RETURNS jsonb
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `p_device` | text | 是 | 设备标识，8–40 位字母数字。前端首次生成后存 localStorage |
| `p_gate_ok` | text | 是 | A-01 返回的标记 |
| `p_ip` | text | 否 | 仅用于新建身份限流 |

**返回 `data`**

```json
{
  "token": "a3f1…（64 位）",
  "user": { "user_id": 12, "device_id": "k3f9…", "nickname": "路过的人" },
  "is_new": false
}
```

| 字段 | 说明 |
|---|---|
| `token` | 会话凭证，前端存 localStorage |
| `is_new` | 本次是否新建了身份。前端据此决定要不要提示「你的恢复码在‘我的经历’里」 |
| `user` | **不含 `recovery_code`**。恢复码只能通过 A-13 单独取，避免它在每次刷新时出现在网络上 |

**错误码**

| 码 | 触发 |
|---|---|
| 40301 | `gate_ok` 无效或已过期（超过 1 小时） |
| 42906 | 同一 IP 24 小时内新建超过 20 个身份 |
| 40001 | `p_device` 格式不合法 |

**实现要点**

```sql
-- 1. 校验 gate_ok（当前小时 + 上一小时）
SELECT value INTO v_hash FROM app_config WHERE key = 'gate_pass_hash';
v_now  := left(encode(digest(v_hash || to_char(now(),                          'YYYYMMDDHH24'), 'sha256'), 'hex'), 32);
v_prev := left(encode(digest(v_hash || to_char(now() - interval '1 hour',      'YYYYMMDDHH24'), 'sha256'), 'hex'), 32);
IF p_gate_ok IS NULL OR p_gate_ok NOT IN (v_now, v_prev) THEN
  RETURN 40301;
END IF;

-- 2. 命中已有设备 → 只更新 last_seen_at
UPDATE app_user SET last_seen_at = now()
 WHERE device_id = p_device
 RETURNING user_id, session_token, nickname INTO v_uid, v_token, v_nick;

IF FOUND THEN
  RETURN jsonb_build_object('code', 0, 'message', '', 'data',
    jsonb_build_object('token', v_token, 'is_new', false,
      'user', jsonb_build_object('user_id', v_uid, 'device_id', p_device, 'nickname', v_nick)));
END IF;

-- 3. 新建设备（先做 42906 计数）
INSERT INTO app_user (device_id, session_token, nickname, recovery_code)
VALUES (p_device, gen_token(), gen_default_nickname(), gen_recovery_code())
RETURNING user_id, session_token, nickname INTO v_uid, v_token, v_nick;
```

**并发**：两个标签页同时 init 同一设备可能都走「新建」分支，靠 `uk_user_device` 兜住——第二个会抛唯一冲突。处理方式：捕获冲突后重查一次并返回已存在那条，**不要**把 `23505` 原样抛给前端。

### A-03 `api_topics` — 主题与条数

**返回 `data`**

```json
{
  "items": [
    { "topic_code": "study", "name": "升学备考", "count": 8, "open": true },
    { "topic_code": "job",   "name": "找工作",   "count": 6, "open": true }
```

### A-04 `api_story_list` — 列表、筛选、分页

**用途**：首页与主题页的主列表。

**签名**

```sql
api_story_list(
  p_token text,

  p_status varchar DEFAULT NULL,

```

| 参数 | 取值 | 说明 |
|---|---|---|
| `p_topic` | 见 3.8，或 null | null = 不限主题 |
| `p_status` | `open` / `resolved` / null | null = 两种都要 |
| `p_keyword` | 1–20 字或 null | 在标题与「当时」正文里做不区分大小写的模糊匹配 |
| `p_page` / `p_size` | 见 2.6 | |

**返回 `data`**

```json
{
  "items": [ { "id": 31, "title": "…", "summary": "…", "status": "open",
               "topic_code": "study", "life_stage": "college", "tags": ["exam"],
               "author_nickname": "…", "created_at": "2026-10-20T03:12:00Z",
               "thanks_count": 4, "updated": false, "is_sample": false } ],

```

| 字段 | 说明 |
|---|---|
| `summary` | `body_before` 前 80 字 + 省略号，由服务端截断。**前端不截断正文**，避免把全文传到浏览器 |
| `updated` | `resolved_at IS NOT NULL`。「更新过」角标的唯一来源（5.5 口径统一） |
| `is_sample` | `source_type = 'qa'`，前端据此打「示例」角标 |

**筛选条件（固定，不可由前端改变）**

```sql
WHERE deleted_at IS NULL
  AND status IN ('open','resolved')      -- hidden / deleted 一律不出现在列表
  AND visibility = 'public'              -- private 只有作者能在「我的经历」看到
```

**排序**：`created_at DESC, story_id DESC`（2.6）。

**错误码**：`40101`、`40001`（size/page 非法）、`50001`

**实现要点**

- `p_status` 传入非法值不要报错，按 null 处理（前端传错不该阻断用户）
- `p_keyword` 用 `ILIKE '%' || p_keyword || '%'`，数据量 ≤ 100 条时够用；超过 500 条再考虑 `pg_trgm`
- `total` 用同一条 WHERE 里的 `COUNT(*) OVER()` 一次查出，**不要发两次查询**

### A-05 `api_story_detail` — 详情

**用途**：详情页。**这是唯一一个「200 但不是正常内容」的接口**（hidden）。

**签名**：`api_story_detail(p_token text, p_story_id bigint) RETURNS jsonb`

**返回 `data`（正常）**

```json
{
  "id": 31, "title": "…",
  "body_before": "…", "body_after": null,
  "status": "open", "visibility": "public",
  "topic_code": "study", "life_stage": "college", "tags": ["exam"],
  "author_nickname": "…", "created_at": "…", "resolved_at": null,
  "thanks_count": 4, "updated": false, "thanked": false,
  "is_author": false, "is_sample": false, "notice": null
}
```

**返回 `data`（hidden）**

```json
{
  "id": 31, "title": "…（标题保留）",
  "body_before": null, "body_after": null,
  "status": "hidden", "thanks_count": 4,
  "is_author": false, "notice": "这条内容正在处理中，暂时无法查看。"
}
```

前端**按 `data.status` 分支**，不按 HTTP 码分支。

**可见性判定（必须严格按这个顺序）**

| 情况 | 返回 |
|---|---|
| 不存在 | `40401` |
| `deleted_at` 非空 | `40401`（与不存在完全一致，不暴露「曾经存在」） |
| `visibility='private'` 且非作者 | `40401`（同上，不暴露「存在但你看不到」） |
| `status='hidden'` 且非作者 | `code=0` + `status='hidden'` + 占位 + `notice` |
| `status='hidden'` 且是作者 | 同上，`notice` 改为「你的这条内容正在处理中」 |
| 其它 | 正常返回 |

**错误码**：`40101`、`40401`、`50001`

**实现要点**

- `is_author` 用 `author_id = v_uid` 判定，**不是** `device_id`
- `thanked` 用 `EXISTS (SELECT 1 FROM thanks WHERE story_id = … AND device_id = 当前设备)`
- `updated` 与列表同口径：`resolved_at IS NOT NULL`

### A-06 `api_story_create` — 发布

**用途**：投稿。V1 唯一需要幂等的接口。

**签名**

```sql
api_story_create(p_token text, p_payload jsonb, p_request_id text DEFAULT NULL) RETURNS jsonb
```

**`p_payload` 结构**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `title` | string | 是 | 4–40 字 |
| `body_before` | string | 是 | 50–2000 字 |
| `body_after` | string | 否 | 50–2000 字 |
| `status` | string | 是 | `open` / `resolved`；`resolved` 时 `body_after` 必填 |
| `topic_code` | string | 是 | 必须是 open 的主题 |
| `life_stage` | string | 是 | 见 3.8 |
| `tags` | string[] | 否 | ≤ 3 个，值必须合法 |
| `nickname` | string | 是 | 2–12 字；与当前昵称不同则视为改名（只能改 1 次） |
| `visibility` | string | 否 | 默认 `public` |

**返回 `data`**

```json
{ "id": 42, "duplicated": false, "needs_review": false }
```

**错误码**

| 码 | 触发 |
|---|---|
| 40001 | 任一字段不合法（`message` 指明是哪个字段） |
| 40101 | token 失效 |
| 42901 | 同一设备 10 分钟内发布超过 3 条 |
| 50001 | 写入异常 |

**幂等流程（先查后插，靠唯一索引兜底）**

```sql
IF p_request_id IS NOT NULL THEN
  SELECT story_id INTO v_id FROM story WHERE request_id = p_request_id;
  IF FOUND THEN
    RETURN jsonb_build_object('code', 0, 'message', '', 'data',
      jsonb_build_object('id', v_id, 'duplicated', true));
  END IF;
END IF;
```

**事务边界**：写 `story` 与写 `story_tag` 必须在同一个 `BEGIN … EXCEPTION` 块里。标签写失败时整条回滚，不留「有内容没标签」的半成品。

**昵称处理**

| 情况 | 行为 |
|---|---|
| `p_payload.nickname` 与当前一致 | 不处理 |
| 不同且 `nickname_changed = 0` | 更新昵称（唯一冲突 → 40001 提示换一个），置 `nickname_changed = 1` |
| 不同且 `nickname_changed = 1` | 40001「昵称只能改一次」，**但内容照常可以发布**——这条是提示，不是阻断。实现上应当忽略新昵称并继续，而不是整单失败 |

**敏感词**：命中则 `needs_review = 1`，**不阻断发布**（RB-19）。自伤类表述同样不阻断，只标记。

### A-07 `api_story_update` — 编辑

**签名**：`api_story_update(p_token text, p_story_id bigint, p_payload jsonb) RETURNS jsonb`

**可改字段**：`title`、`body_before`、`body_after`、`topic_code`、`life_stage`、`tags`、`visibility`

**不可改**：`status`（用 A-08 补写）、`author_id`、`created_at`

**权限**：`story.author_id = v_uid`，否则 `40401`（**不是 40301**——不暴露「这条存在但不归你」）

**错误码**：`40001`、`40101`、`40401`、`40901`（编辑期间状态被改成 hidden/deleted）、`50001`

**实现要点**：先 `SELECT … FOR UPDATE` 锁行再校验状态，避免「读到 open、写时已 resolved」的竞态。

### A-08 `api_story_resolve` — 补写「后来」

**签名**：`api_story_resolve(p_token text, p_story_id bigint, p_body_after text) RETURNS jsonb`

**前置条件**

| 条件 | 不满足时 |
|---|---|
| 是作者 | `40401` |
| `status = 'open'` | `40901`「这条已经补写过了」 |
| `body_after` 50–2000 字 | `40001` |

**写入**：`body_after = …`，`status = 'resolved'`，`resolved_at = now()`，`updated_at = now()`。

三者必须同时改：DB 有 CHECK 约束（`ck_story_after_by_status`、`ck_story_resolved_at`），漏改任何一个都会直接抛约束错。

**错误码**：`40001`、`40101`、`40401`、`40901`、`50001`

**并发**：两个标签页同时补写，靠 `FOR UPDATE` + 状态复查串行化；第二个进来时状态已是 resolved，返回 `40901`。

### A-09 `api_story_delete` — 删除

**签名**：`api_story_delete(p_token text, p_story_id bigint) RETURNS jsonb`

**行为**：软删除，置 `deleted_at = now()`，`status = 'deleted'`。**不物理删除**，V1.1 的后台处置与申诉要能查到历史。

**权限**：作者本人。否则 `40401`。

**幂等**：已删除再删一次，返回 `code=0`，不报错。

**连带**：`thanks` 与 `story_tag` **不删**——计数与标签留着，恢复后还能用；列表与详情已按 `deleted_at` 过滤，不会露出。

**错误码**：`40101`、`40401`、`50001`

### A-10 `api_story_thanks` — 致谢（简略）

**签名**：`api_story_thanks(p_token text, p_story_id bigint) RETURNS jsonb`

**返回**：`{ "thanks_count": 5, "thanked": true }`

**规则**

| 情况 | 返回 |
|---|---|
| 首次致谢 | `code=0`，计数 +1 |
| 重复致谢 | `code=0`，计数不变（**不是 409**，前端不该弹错误） |
| 给自己的内容致谢 | `41001`「不能给自己的内容致谢」 |
| 示例内容 | `41001`「示例内容不支持致谢」 |
| 内容已隐藏 / 删除 | `41001` |

**实现**：`INSERT INTO thanks … ON CONFLICT DO NOTHING`，再用 `RETURNING` 判断是否真的插入，只在插入成功时 `thanks_count + 1`。两个动作同事务。

### A-14 `api_recovery_reset` — 主动重置恢复码

**签名**：`api_recovery_reset(p_token text) RETURNS jsonb`

**行为**：生成新码，旧的立即失效。返回 `{ "recovery_code": "新码" }`。

**为什么要有这个接口**：恢复码是唯一凭证，一旦截图外泄就是永久失控。重置是用户唯一能自救的手段（R9-8）。

**风险（必须写进产品文案）**：重置后新码只存在于当前设备。若该设备随后损坏，内容永久丢失。前端在确认弹层里必须原样告知。

**错误码**：`40101`、`50001`

### A-15 `api_claim` — 认领迁移

**用途**：用恢复码把内容迁到当前设备。**整个产品唯一不可逆的操作**，也是唯一必须防并发的地方。

**签名**

```sql
api_claim(p_token text, p_new_device text, p_code text, p_ip text DEFAULT NULL) RETURNS jsonb
```

| 参数 | 说明 |
|---|---|
| `p_token` | 当前设备的 token（可为 null，首次打开时还没有） |
| `p_new_device` | 当前设备标识 |
| `p_code` | 用户输入的 12 位恢复码，前端去掉连字符与空格后传出 |
| `p_ip` | 失败计数用 |

**返回 `data`**

```json
{ "token": "…（新）", "user": { "user_id": 12, "device_id": "当前设备", "nickname": "…" },
  "moved": 3 }
```

**错误码**

| 码 | 触发 | 说明 |
|---|---|---|
| 40103 | 码不存在 / 已被使用 / 格式错 | **三者合并，不区分**（E9-1 反探测） |
| 42902 | 同一 IP 10 分钟失败 5 次 | |
| 40001 | `p_new_device` 格式非法 | |
| 50001 | 迁移异常 | |

**实现要点（顺序不能换）**

```sql
-- 1. 行锁取出目标用户
SELECT user_id, device_id, recovery_code INTO v_uid, v_old_device, v_old_code
  FROM app_user WHERE recovery_code = v_norm_code FOR UPDATE;

IF NOT FOUND THEN
  -- 失败计数（42902 判定）
  RETURN jsonb_build_object('code', 40103, 'message', '恢复码不对，或者已经被用过了');
END IF;

-- 2. 清掉新设备上的空白身份（若有）
--    不清就会撞 uk_user_device，整个迁移失败
DELETE FROM app_user
 WHERE device_id = p_new_device AND user_id <> v_uid
   AND NOT EXISTS (SELECT 1 FROM story WHERE author_id = app_user.user_id);

-- 3. 换设备、换 token、换码、刷新活跃时间
UPDATE app_user
   SET device_id     = p_new_device,
       session_token = gen_token(),
       recovery_code = gen_recovery_code(),
       last_seen_at  = now()
 WHERE user_id = v_uid
 RETURNING session_token, nickname INTO v_token, v_nick;

-- 4. story 一行都不动（判权靠 author_id）
```

**三个坑**

| 坑 | 后果 | 处理 |
|---|---|---|
| 忘记清空新设备的空白身份 | `uk_user_device` 冲突，迁移整体失败 | 第 2 步 |
| 第 2 步删错了人 | 删掉一个**有内容**的用户，内容变孤儿 | `NOT EXISTS (… story …)` 保护 |
| 迁移成功后旧设备仍持有旧 token | 旧设备还能读写 | 换 `session_token` 时旧值自然失效（token 唯一） |

**「响应丢失」的补偿**：服务端已迁移、响应在路上丢了，用户重试会拿到 `40103`（旧码已失效），以为自己丢了内容。因此前端在失败后要**额外查一次「当前设备是否已经有身份且有内容」**（调 A-12），有则提示「其实已经成功了」而不是「恢复码错误」。这是 PRD E9-4 要求的行为，实现上必须有这个分支。

## 第 5 章 鉴权与安全

### 5.1 凭证与生命周期

| 凭证 | 存放 | 生命周期 | 产生 | 失效 |
|---|---|---|---|---|
| `gate_ok` | sessionStorage | 1 小时 | A-01 | 过期；口令变更 |
| `session_token` | localStorage | 长期 | A-02 / A-15 | 认领迁移、重置恢复码、用户清缓存 |
| `device_id` | localStorage | 长期 | 前端首次生成 | 清缓存。**它不参与判权**，只是认人的线索 |
| `request_id` | sessionStorage | 一次表单会话 | 前端打开表单时 | 提交成功后清掉 |

**判权唯一依据是 `story.author_id`**。`device_id` 只在「找我是谁」这一步用（A-02 查行），一旦拿到 `user_id`，后续所有判断都不再看设备。

这条规则的意义：换设备时只更新 `app_user` 一行，`story` 表零改动。V1.2 用 `author_device_id` 判权，导致换设备后旧内容全部读不到，是整份设计里最严重的一个错误。

### 5.2 权限矩阵

| 操作 | 未进站 | 已进站（非作者） | 作者本人 | 说明 |
|---|---|---|---|---|
| 看公开列表 | ✗ 40301 | ✓ | ✓ | 未进站一律拦在门页 |
| 看 public 详情 | ✗ | ✓ | ✓ | |
| 看 private 详情 | ✗ | ✗ 40401 | ✓ | 40401 与「不存在」一致 |
| 看 hidden 详情 | ✗ | 占位 + 提示 | 占位 + 提示 | 不是 404 |
| 发布 | ✗ | ✓ | ✓ | 限流 3 条 / 10 分钟 |
| 编辑 / 删除 | ✗ | ✗ 40401 | ✓ | |
| 补写「后来」 | ✗ | ✗ 40401 | ✓ | 且仅 open 状态 |
| 致谢 | ✗ | ✓ | ✗ 41001 | 示例内容也不可致谢 |
| 看「我的经历」 | ✗ | 只看到自己的 | ✓ | |
| 看恢复码 / 重置 | ✗ | 只看到自己的 | ✓ | |

**统一的拒绝方式**：与「不存在」返回同一个码（`40401`），不给探测者区分「无权」与「不存在」的机会。

### 5.3 数据可见性矩阵

| `visibility` | `status` | 公开列表 | 公开详情 | 我的经历 | 说明 |
|---|---|---|---|---|---|
| public | open | ✓ | ✓ | ✓ | 常态 |
| public | resolved | ✓ | ✓ | ✓ | 常态 |
| public | hidden | ✗ | 占位 | ✓（按钮置灰） | 被治理 |
| public | deleted | ✗ | 40401 | ✗ | 软删 |
| private | open / resolved | ✗ | 仅作者 | ✓ | 私密记录 |
| private | hidden | ✗ | 占位（仅作者） | ✓ | |
| 任意 | 任意 | — | — | — | `source_type='qa'` 的计入可见但**不计条数、不可致谢** |

### 5.4 限流实现

计数表 3.7，判定在函数内：

```sql
-- 窗口起点：按窗口长度截断
v_window := to_timestamp(floor(extract(epoch FROM now()) / 600) * 600);  -- 10 分钟

INSERT INTO rate_limit (bucket, subject, window_start, hit_count)
VALUES ('publish', v_device, v_window, 1)
ON CONFLICT (bucket, subject, window_start)
DO UPDATE SET hit_count = rate_limit.hit_count + 1
RETURNING hit_count INTO v_hits;

IF v_hits > 3 THEN
  RETURN jsonb_build_object('code', 42901, 'message', '刚发过几条了，歇一会儿再写');
END IF;
```

`ON CONFLICT DO UPDATE` 保证并发下计数不丢；这是 PG 少见的「一次语句完成读改写」的写法，比先 SELECT 再 UPDATE 安全。

### 5.5 安全红线

| # | 红线 | 违反的后果 |
|---|---|---|
| 1 | 恢复码不进日志、不进错误响应、不进埋点 | 日志被看到 = 所有内容被接管 |
| 2 | 口令只存哈希，永不回显 | 同库泄露时口令直接暴露 |
| 3 | 用户内容一律 `textContent` 写入，不拼 `innerHTML` | XSS 可窃取 localStorage 里的 token |
| 4 | 表对 `anon` 零授权，需要数据就加函数 | 一次 `GRANT SELECT` 会绕过全部函数层校验 |
| 5 | 不引第三方脚本 | 任何外部脚本都能读 localStorage |

**第 3 条的具体做法**（前端实现要求）：

```js
// 对
el.textContent = s.title;

// 错
el.innerHTML = `<h3>${s.title}</h3>`;
```

判断标准是「这段字符串里有没有用户输入」，不是「有没有用 innerHTML」。静态骨架（骨架屏、空态、状态标签）用 `innerHTML` 没问题。

**XSS 缓解只能是这三条**：不解析用户输入、不引外部脚本、认领/重置换发 token。**不要**声称「token 放 localStorage 是安全的」——它不是，只是这个产品在「点开就能用」和「安全」之间选了前者。

## 第 6 章 前端设计（对照高保真原型）

### 6.1 原型是什么、能复用什么

| 事实 | 结论 |
|---|---|
| 原型 `人生的路你走到哪了.html` 是**打包后的 React 应用**（radix 组件编译进 JS），HTML 里没有可读的 `class` | 结构不能直接复用 |

**做法**：结构重写、视觉照抄、素材复用。不引入 React，因为 V1 只有 5 个页面，且要求「打开就能看」。

| `data.status` + 角色 | 渲染 |
|---|---|

## 第 7 章 关键时序

### 7.1 首次进入

```
用户点链接
   │
   ├─ index.html 加载 → api.js 初始化 SDK
   │
   ├─ 有 token？ ──有──▶ 直接调 A-03/A-04
   │       │
   │      没有
   │       ▼
   │  有 gate_ok？ ──有──▶ A-02 换 token ──▶ 正常
   │       │
   │      没有
   │       ▼
   └─▶ 跳 gate.html → 输入口令 → A-01 → gate_ok → A-02 → token → 回首页
```

**失败分支**：A-01 返回 40301 → 门页原地提示「口令不正确」；42903 → 提示「试得有点多，稍后再试」，输入框置灰。

### 7.2 发布（含幂等）

```
打开 write.html
   │  生成 request_id 存 sessionStorage；读本地草稿
   ▼
第 1 步：写标题 + 「当时」  ──本地校验（长度、必填）
第 2 步：选主题 + 阶段 + 标签
第 3 步：填昵称 + 勾选合并确认（18 岁 + 内容将公开展示）
   │
   ▼
[预览] → 渲染只读视图（不请求服务端）
   │
[发布] → A-06
   │
   ├─ code=0, duplicated=false → 清 request_id、清草稿 → 跳详情页
   ├─ code=0, duplicated=true  → 提示「这次已经提交成功了」→ 跳详情页
   ├─ 40001 → 定位到出错字段并提示，保留已填内容
   └─ 42901 → 提示稍后再试，保留内容
```

**草稿**：每步输入变化 800ms 防抖写 localStorage（key `renlu.draft`），发布成功或用户手动清空时删除。**草稿不写服务端**（V1）。

### 7.3 补写「后来」

```
详情页（作者视角，status=open）→ [补写后来] → 弹层输入 50–2000 字
   │
   ▼ A-08
   ├─ code=0 → 重新拉 A-05，页面切到 resolved，显示两区块
   ├─ 40901 → 「这条已经补写过了」→ 重新拉详情
   └─ 40001 → 字数提示
```

### 7.4 认领迁移（唯一不可逆）

```
旧设备丢了 / 换了手机
   │
   ▼
新设备打开 claim.html → 输入 12 位恢复码
   │
   ▼ A-15
   ├─ code=0        → 存新 token → 跳「我的经历」，显示 moved 条
   ├─ 40103         → ① 先查 A-12 看当前设备是否已有内容
   │                    有 → 提示「其实已经迁移成功了」（响应丢失的补偿）
   │                    无 → 提示「恢复码不对，或者已经被用过了」
   └─ 42902         → 提示稍后再试
```

### 7.5 我的经历 + 恢复码

```
me.html
  ├─ A-12 列表：每条显示状态、天数、可用操作
  ├─ [查看恢复码] → A-13 → 展示（可复制，不自动复制）
  └─ [重置恢复码] → 二次确认（明确告知「旧码立即失效，新码只显示这一次」）
```

## 第 8 章 实施与验证

### 8.1 建库顺序

必须按这个顺序，跳步会报错：

| # | 步骤 | 说明 |
|---|---|---|
| 1 | `CREATE EXTENSION IF NOT EXISTS pgcrypto` | `crypt()` / `digest()` 依赖它 |
| 2 | 建 6 张表（`schema.sql` 前半） | 表之间按 app_user → story → thanks / story_tag 顺序 |
| 3 | 建索引 | 在灌数据之前建，避免后建锁表 |
| 4 | `REVOKE ALL ON ALL TABLES / SEQUENCES FROM anon, authenticated` | **必须在建函数之前**，否则先授权就等于开了口子 |
| 5 | 写 `app_config` 三行 | `gate_pass_hash` 用 `crypt('口令', gen_salt('bf'))` 生成 |

| 7 | `REVOKE EXECUTE … FROM PUBLIC` + `GRANT EXECUTE … TO anon` | 逐个函数 |
| 8 | 灌种子数据 | 示例 6 条 + 首批真实内容 |

## 附录 A 错误码全表

| 码 | 含义 | 触发接口 | 前端动作 |
|---|---|---|---|
| 0 | 成功 | 全部 | 正常渲染 |
| 40001 | 参数不合法 | 写接口、A-15 | 定位字段提示，用 `message` 原文 |
| 40101 | token 缺失或失效 | 除 A-01、A-02 | 重新 init 后重试一次；仍失败则回门页 |
| 40103 | 恢复码不正确或已被用过 | A-15 | 统一提示；先查 A-12 做「其实已成功」补偿 |
| 40301 | 未通过口令 / 口令错误 | A-01、A-02 | 门页原地提示 |
| 40401 | 不存在、无权访问或已删除 | A-05、A-07、A-08、A-09 | 统一「不存在」，不区分原因 |
| 40901 | 状态冲突 | A-07、A-08 | 刷新页面 |
| 41001 | 内容状态已变化 / 不可致谢 | A-10 | 刷新详情 |
| 42901 | 发布过于频繁 | A-06 | 「稍后再试」，不暴露阈值 |
| 42902 | 认领失败过多 | A-15 | 同上 |
| 42903 | 口令失败过多 | A-01 | 同上，输入框置灰 |
| 42906 | 新建身份过多 | A-02 | 同上 |
| 50001 | 服务异常 | 全部 | 通用错误 + 重试按钮 |

**约定**：`message` 是可以直接展示的中文，前端不二次翻译；所有码都在响应体 `code` 字段里，HTTP 恒 200。

**关于 42501**：这是 PostgreSQL 的权限错误（缺表授权或被策略拒绝），**不是业务码**，正常不应出现在任何响应里。一旦出现，说明有代码绕过了函数直接访问表，或建库时的授权收口漏了某张表——排查方向见 8.1 第 4 步。

## 附录 B 与 PRD 的差异

| 项 | PRD | 本设计 | 原因 |
|---|---|---|---|
| 接口形态 | REST 路径 + HTTP 方法 | 14 个 PostgreSQL 函数 | 平台无自定义服务端，只有 SQL 函数 |
| 接口数 | 18 | 14 | V1 只做 F0–F10；举报与后台属 V1.1 |
| 鉴权 | HttpOnly Cookie + `X-Device-Id` | `gate_ok` + `session_token` | 平台下发不了 Cookie，读不到自定义头 |
| 错误表达 | HTTP 状态码 + `code` | 仅响应体 `code` | 函数改不了状态码 |
| 表数 | 6（含 report、admin_log） | 6（去 report/admin_log，加 app_config、rate_limit） | 举报与后台延后；配置与限流缺了没处放 |
| 配置 | 环境变量 | `app_config` 表 | 平台无环境变量注入 |
| 口令标记 | 30 天 Cookie | 1 小时 `gate_ok` + 长期 token | 没有可签名的密钥，用「哈希 + 小时」替代 |
| 筛选维度 | 主题（RS-3） | 主题（同 PRD） | 原型是阶段，见 6.7 待定项 D-01 |

**PRD 下个修订需要跟改的两处**：F0 的「HttpOnly Cookie、30 天」改为 token 方案；NF-08 的「口令放环境变量」改为 `app_config`。其余差异属实现层，PRD 第 9 章的 18 个接口作为完整规格仍然成立。
